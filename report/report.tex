\section{Glossary of the Haskell Type System}
Before investigating kinds, we briefly explain the most important definitions in Haskell's type system and make example(s).
\subsubsection*{Type}
A type classifies values and expressions; it describes what kind of data something is and which operations are valid on it.
\begin{lstlisting}
    Int, Bool, Char
    [Int]
    int -> Bool
    Maybe Int
\end{lstlisting}
\subsubsection*{Type Signature}
A type signature is an explicit annotation of an expression’s type.
\begin{lstlisting}
    not :: Bool -> Bool
\end{lstlisting}
\subsubsection*{Type Variable}
A type variable is a placeholder for an unknown type, enabling polymorphism. Usually written \texttt{a}, \texttt{b}, \texttt{t}, etc.
\begin{lstlisting}
    id :: a -> a -- Here the type signature of "id" contains type variables
\end{lstlisting}
\subsubsection*{(Parametric) Polymorphism}
Parametric polymorphism means code works uniformly for any type, without inspecting that type.
\begin{lstlisting}
    length :: [a] -> Int
\end{lstlisting}
\subsubsection*{Type Constructor}
A type constructor is something that builds new types from type parameters (a "type-level function").
\begin{lstlisting}
    [] :: Type -> Type
    Maybe :: Type -> Type
    Either :: Type -> Type -> Type
\end{lstlisting}
\subsubsection*{(Data) Constructor}
A data constructor builds values, not types.
\begin{lstlisting}
    Just :: a -> Maybe a
    Nothing :: Maybe a
\end{lstlisting}
\subsubsection*{Type Class}
A type class defines a set of operations (methods) and laws that a type can implement. It’s like an interface/contract at the type level.
\begin{lstlisting}
    class Eq a where
        (==) :: a -> a -> Bool
\end{lstlisting}
\subsubsection*{Type Constraint}
A type constraint restricts a type variable to types that are instances of some type class(es). Written before \texttt{=>} in a type signature.
\begin{lstlisting}
    (==) :: Eq a => a -> a -> Bool
    foo :: (Eq a, Show a) => a -> String
\end{lstlisting}
\subsubsection*{Constrained Polymorphism}
When a function is polymorphic but only for types satisfying constraints (type classes), it’s constrained (often called ad-hoc polymorphism).
\begin{lstlisting}
    show :: Show a => a -> String
\end{lstlisting}


\section{Kinds in Haskell}
Haskell offers besides a classical typesystem a "type system of a type system", also called \textit{kinds} (i.e. kind of a type or type of a type). In GHCI, the interactive haskell interpreter, we can use the \texttt{:t} command to check the type of a previously declared variable:
\begin{lstlisting}
    ghci> x = 42 :: Int
    ghci> :t x
    x :: Int
\end{lstlisting}
Now, the type \texttt{Int} has the following kind, which we can check using the \texttt{:k} command:
\begin{lstlisting}
    ghci> :k Int
    Int :: *
\end{lstlisting}
In contrast, we can check the kind of a type constructor such as \texttt{Maybe}:
\begin{lstlisting}
    ghci> :k Maybe
    Maybe :: * -> *
\end{lstlisting}
\texttt{Maybe} is a type constructor, meaning it takes an additional type as an argument, which will then produce the kind:
\begin{lstlisting}
    ghci> :k Maybe Int
    Maybe Int :: *
\end{lstlisting}
More complex kinds are also possible:
\begin{lstlisting}
    ghci> :k Either
    Either :: * -> * -> *
    ghci> :k (->)
    (->) :: * -> * -> *
\end{lstlisting}
Under the hood GHC, the Haskell Compiler, treats kinds as types, meaning internally mostly the same procedures are used to check the correctness of types and kinds.

\subsection{Higher-kinded Types}
A higher-kinded type is a type constructor taking a type constructor as an argument:
\begin{lstlisting}
    ghci> :k Functor
    Functor :: (* -> *) -> Constraint
\end{lstlisting}
Here \texttt{Constraint} is the kind of type constraints. We can test the \texttt{Functor} kind by supplying different types or type constructors:
\begin{lstlisting}
    ghci> :k Functor Maybe
    Functor Maybe :: Constraint
    ghci> :k Functor Int

    <interactive>:1:9: error:
        - Expected kind '* -> *', but 'Int' has kind '*'
        - In the first argument of 'Functor', namely 'Int'
        In the type 'Functor Int'
\end{lstlisting}
Higher-kinded types allow the programmer to abstract over type constructors, meaning we can write functions that work for any type constructor of the same kind (or arity). In other programming languages, we can only quantify over types, but not type constructors (taking types as arguments). A programmer can write a function that works for any \texttt{f :: * -> *} or even any \texttt{p :: * -> * -> *}. For example, we can write a utility function that converts to elements implementing the \texttt{Show} typeclass to strings in any (data) structure implementing the \texttt{Functor} typeclass:
\begin{lstlisting}
    liftAndShow :: (Functor f, Show a) => f a -> f String
    liftAndShow = fmap show
\end{lstlisting}
This works only with higher-kinded types because \texttt{Functor} needs a higher-kinded parameter:
\begin{lstlisting}
    class Functor (f :: * -> *) where
        fmap :: (a -> b) -> f a -> f b
\end{lstlisting}
Another example is the function \texttt{sequence} that evaluates every action in a list of monads and collects the results:
\begin{lstlisting}
    sequence :: Monad m => [m a] -> m [a]
\end{lstlisting}
Here, \texttt{m} is higher-kinded: \texttt{m :: * -> *}.



\subsection{Other Kinds}
\subsubsection*{DataKinds}
With \texttt{DataKinds}, constructors can be used as types.
\begin{lstlisting}
    {-# LANGUAGE DataKinds #-}
    import Data.Kind (Type)

    data Nat = Z | S Nat
\end{lstlisting}
Now, new types or type constructors are created for the constructors, prefixed by \texttt{'}:
\begin{lstlisting}
    Nat :: *
    'Z :: Nat
    'S :: Nat -> Nat
\end{lstlisting}
\subsubsection*{PolyKinds}
With \texttt{PolyKinds}, GHC can infer kind-polymorphic definitions.
\begin{lstlisting}
    {-# LANGUAGE PolyKinds #-}
    data Proxy (a :: k) = Proxy
\end{lstlisting}
Here \texttt{k} is a kind variable, and the constructor is kind-polymorphic:
\begin{lstlisting}
    Proxy :: forall k. k -> *
\end{lstlisting}
This is similar to polymorphic types, but at the kind level.


\section{Kinds in F\#}
In F\#, there is no distinct kind or type-of-types system, but different type constructors take different number of type arguments, meaning Haskell kinds are most similar to the arity of type constructors in F\#. Types and type constructors with different arities in F\#:
\begin{lstlisting}
    int // no parameters
    'T option // one parameter
    Result<'T, 'E> // two parameters
\end{lstlisting}
Where F\# lacks in comparison to Haskell is higher-kinded types. There is no polymorphism over type constructors. We cannot express, at the type level, that a generic type parameter is itself a type constructor of a particular arity (e.g. something that takes a type argument), in Haskell this is expressed and enforced by the kind system. We cannot, for example, write a generic implementation of a \texttt{map} function for any unary type constructor. So, we can write the following in F\#:
\begin{lstlisting}
    let incList xs = List.map ((+) 1) xs
    let incOption x = Option.map ((+) 1) x
\end{lstlisting}
But not:
\begin{lstlisting}
    let incAny (x : F<int>) = map ((+) 1) x
\end{lstlisting}
Generics in F\# only work for types, not type constructors. Furthermore, there is no equivalent to Haskell's DataKinds and PolyKinds.

A Workaround that is usable in F\# is representing the higher-kinded type using a generic type with two type variables, with the first type variable being a "witness/tag" type, indicating what type constructor it is, for example \texttt{Option} or \texttt{List}, and the second type variable being the element type, for example \texttt{int}. The result is a type like \texttt{App<'F, 'T>}, which during runtime is just a boxed object. Because this is a runtime solution to a static typing problem, the construct does not enforce that the object contains the correct type specified in the witness type variable. An example code snippet:
\begin{lstlisting}
    // HKT encoding: "F applied to T"
    type App<'F, 'T> = private App of obj

    // Example tags
    type OptionTag = class end
    type ListTag = class end

    module HKT =
    let inline inj (x: 'Real) : App<'F,'T> = App (box x)
    let inline prj (App o) : 'Real = unbox o

    type Functor<'F> =
    { Map : ('a -> 'b) -> App<'F,'a> -> App<'F,'b> }

    // Instances
    let optionFunctor =
    { Map =
        fun f fa ->
            let x : option<_> = HKT.prj fa
            HKT.inj (Option.map f x) }

    let listFunctor =
    { Map =
        fun f fa ->
            let x : list<_> = HKT.prj fa
            HKT.inj (List.map f x) }
\end{lstlisting}
Here, the \texttt{inj} and \texttt{prj} functions allow to pack or unpack the acutal objects into the encoded representation (\texttt{App<'F, 'T>}).

Another approach is to wrap values in an object that exposes the operations we need, such as \texttt{map} in our example. We create a common interface, for example an interface resembling functors:
\begin{lstlisting}
type IFunctor<'T> =
    abstract Map<'U> : ('T -> 'U) -> IFunctor<'U>

type OptionF<'T>(x: option<'T>) =
    member _.Value = x
    interface IFunctor<'T> with
        member _.Map f = OptionF(Option.map f x) :> IFunctor<_>

type ListF<'T>(x: list<'T>) =
    member _.Value = x
    interface IFunctor<'T> with
        member _.Map f = ListF(List.map f x) :> IFunctor<_>
\end{lstlisting}
Usage of the wrapper objects:
\begin{lstlisting}
    let a : IFunctor<int> = OptionF(Some 1) :> IFunctor<_>
    let b : IFunctor<string> = a.Map string
\end{lstlisting}
This approach is what would be used in standard object-oriented programming. One downside is that you have to wrap every type constructor with the interface; stacking abstractions such as Functor, Applicative and Monad like in Haskell is not possible without writing many interfaces. Additionally, you program against a interface (\texttt{IFunctor<'U>}), so you cannot statically know if it is \texttt{OptionF<'U>} or \texttt{ListF<'U>}, you will program against the common functor interface, while in Haskell, you will preserve the type constructor's type. Because of this, this approach is not equivalent to Haskell's higher-kinded type system.


\section{Kinds in JavaScript}
JavaScript has also no kind system, it does not even have a static type system. To achieve higher-kind-like reasoning in TypeScript, we can employ the same methods previously described for F\#. For the first variant using a generic type with two type variables, one being a "witness/tag" type and the other type variable being the element type, we can model it in TypeScript:
\begin{lstlisting}
    interface URItoKind<A> {
        Array: Array<A>;
        Option: Option<A>;
    }
    type URIS = keyof URItoKind<any>;

    type Kind<URI extends URIS, A> = URItoKind<A>[URI];

    interface Functor<URI extends URIS> {
        readonly URI: URI;
        map: <A, B>(fa: Kind<URI, A>, f: (a: A) => B) => Kind<URI, B>;
    }

    const arrayFunctor: Functor<"Array"> = {
        URI: "Array",
        map: (fa, f) => fa.map(f),
    };
\end{lstlisting}
Here \texttt{Kind<URI, A>} represents the higher kinded type, where \texttt{URI} is a name to map the concrete type constructor, like \texttt{Array} or \texttt{Option} and \texttt{A} the element the type constructor is applied to. This gives us polymorphism over type constructors, but requires some boilerplate that does not feel like native TypeScript.


Also, we could use the second approach proposed for F\#, wrapping values in an object exposing the methods we need, such as \texttt{map}. Again, then we only program against a common interface instead of the true types, which makes this approach inferior to Haskell's higher-kind type system.


\section{Conclusion}
Haskell's kind system is similar to the arity of generics in other programming languages with the difference being that it is a fully-fletched type system for types. Also, it allows for higher-kinded types, which allows for polymorphism over type constructors, something that is not possible in the other languages. Replicating these abstractions in F\# and Typescript requires lots of boilerplate code and programmer discipline or comes with downsides such as losing the identity of container types. All-in-all, the kind system allows for better compile-time safety but is an advanced concept not directly obvious for programmers coming from other languages.
